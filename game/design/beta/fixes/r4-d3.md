## Analysis: the hung 4x scripts (b13 "could not test"): a real bug, fixed
Reproduced on this box: Deepdelve `?test=1`, 390x844 touch, 4x CPU, random taps 700 ms apart: tap 0 took 0.2 s, tap 1 took 20 s,
tap 2 never returned (the script sat at 0% CPU, as b13 saw). Steps to the cause:
1. Each `touchscreen.tap` waits for the renderer to ack the touch; the renderer main thread was inside long tasks of 4-17 s.
2. Those long tasks were not game JavaScript: every rAF callback in the same window took <= 214 ms (wrapped requestAnimationFrame).
3. The same page with no taps for 20 s ran fine; `__dd.aim()` without input ran fine (0 long tasks); ONE touch tap dropped the page
   from ~300 to ~16-28 frames per 5 s with long tasks up to 1.2 s, even at 1x, and `document.pointerLockElement` was the canvas.
4. Cause: a touch tap fires a compatibility `mousedown`, and Deepdelve's `mousedown` handler called `requestPointerLock()`. With
   pointer lock stubbed out the same tap costs nothing (292 frames, 0 long tasks). On a touch laptop / tablet with Chrome this
   captured and hid the mouse pointer on a finger tap; in the emulator it also starved the page.
5. Fix (deepdelve.js): `mousedown` ignores presses that come from touch / pen; a real mouse press still locks (mouse-look). Test
   `beta-r4-deepdelve-touch-lock` fails on the old file (locked, 57 -> 14 fps) and passes now.
The other hung script (Realm soak with taps) ran to completion here for 6 minutes at 4x; Realm never requests pointer lock (no
other `requestPointerLock` in game/). The new soak test races every Playwright step against a timeout, so a stall reports instead
of hanging.
