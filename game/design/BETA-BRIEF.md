# Beta test brief (owner-requested beta, 2026-11-23). Read fully before you start.

You are one of 15 independent beta testers. You PLAY the game for about 60 minutes of wall-clock time (check `date -u`; your deadline is in your prompt) and report what you find. You do NOT fix code. A separate team of 5 development agents (Lead Architect, Gameplay, World+Graphics, Performance+Systems, QA+Integration) will triage and fix from your reports, so reports must be precise and reproducible.

## Setup
`git checkout -B <your-branch> claude/animal-crossing-game-7z3roh` in your worktree (the current tip), then start your own static server: `(setsid nohup python3 -m http.server <port> >/dev/null 2>&1 &)` from the repo root. Game root: http://localhost:<port>/game/ (Hub Home: /game/hub/index.html; Town: /game/index.html?from=hub; Realm: /game/games/mad-maze/index.html?mode=world; Isles: /game/games/isles/index.html; mini games under /game/games/<name>/). ## Rules that never bend
Firebase is LIVE with real players: NEVER send chat, never write/delete in it, never run live multiplayer against real players. Block the database in every browser context you open (helper `blockDb(ctx)` in game/tests/helpers.js blocks both route and routeWebSocket) or use the Town OFFLINE stub (game/tests/nav-town.test.js pattern, 'Play offline'). Only the multiplayer tester may join the live presence, only with ADMIN* names + unique suffix, presence only, under `flock /tmp/live.lock`, never chat. Do not edit game code (docs and screenshots only in your branch). No secrets in reports.

## How to play (be a real player, not a unit test)
Use Playwright (require('playwright') works; Chromium preinstalled, headless, software rendering). Drive the game like a human: real mouse/keyboard/touch events, realistic pauses, explore, make mistakes, read every text, try every button and menu, die, retry, fight, loot, buy, craft, quit and come back, change settings, rotate the phone, use the Menu/back button, leave and re-enter areas. Mix phone (390x844 touch, isMobile) and desktop (1280x720). Take screenshots often (`page.screenshot`) and READ them with the Read tool: judge visuals (clipping, wrong scale, flat/ugly art, text overlap, unreadable text, inconsistent style), not just logic. For real-time feel, record short clips when useful: create the context with `recordVideo: {dir, size}` and keep a clip ONLY for P0/P1 findings (trim with `ffmpeg -t 8`, <= 1.5 MB each, max 4 clips). Use `page.on('console'|'pageerror'|'requestfailed')` and log every error. You may read game source to understand a bug and name the suspect file/line, but you only report.
Machine: 4 cores shared by 20 agents: wrap EVERY browser/node command in `/tmp/bt.sh <command>` (5-slot semaphore); keep each command under ~3 minutes; do not hold a browser open idle between commands (script a play session, run it, read the screenshots/logs, then plan the next one). Think like a tester: what would a new player do? what would a hardcore player exploit? what breaks under stress?

## Report format (mandatory)
1. `game/design/beta/<id>.json`: array of findings: {"id":"<id>-NN","severity":"P0|P1|P2|P3","area":"...","title":"...","steps":["..."],"expected":"...","actual":"...","viewport":"390x844|1280x720","url":"...","screenshots":["img/<id>-NN.png"],"clip":"img/<id>-NN.mp4 or null","suspect":"file:line or null","kind":"bug|visual|perf|ux|balance|improvement","frequency":"always|often|sometimes|once"}.
2. `game/design/beta/<id>.md`: summary: what you covered (areas/systems/time spent), coverage gaps you did not reach, top 10 findings in prose, what felt great, game-readiness score 1-10 for your area, and what you could NOT test and why.
3. Screenshots in `game/design/beta/img/` named `<id>-NN.png`, each <= 250 KB (resize/JPEG-compress if needed; use .jpg then), max 12 images.
Severity: P0 = data loss, crash/freeze, soft-lock, security, cannot progress; P1 = major mechanic broken, very visible visual bug, severe perf problem, unfair/blocked flow; P2 = noticeable bug/visual/UX issue with a workaround; P3 = polish/nit/improvement. Be honest: do not invent findings; if you cannot reproduce twice, mark frequency 'once'. Check `git log` / game/design/bugbash/*.md first so you do not re-report already known open items (you may confirm them with new evidence).
